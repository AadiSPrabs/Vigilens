# Vigilens Render runbook (FREE tier, BYOK demo)

Scope: free Render web services + free Postgres, synthetic transport. No paid
calls, no live provider dispatch. Aadi operates the Render dashboard; this file
is the operator reference. Deploy itself is an account resource mutation and
happens only on Aadi's explicit go.

## Services (render.yaml)

- `vigilens-backend` (python, free): `pip install -r backend/requirements.txt`,
  start `python backend/run_render.py`. Binds 0.0.0.0 on Render's PORT.
- `vigilens-frontend` (node, free): `pnpm install --frozen-lockfile && pnpm build`,
  start `node frontend/.output/server/index.mjs`.
- `vigilens-db` (free Postgres, 1GB, one per workspace). Shared by better-auth
  (frontend) and the pipeline store (separate table namespaces).

## Environment

Backend:
- `VIGILENS_DATABASE_URL` - the database's INTERNAL connection string from the
  Render dashboard. The boot appends `sslmode=require` when the internal
  hostname lacks it (supported internally; verify-ca/full are not). Never
  logged, never written to a file. When set, the journal, preserved artifacts
  and pinned carry/approvals documents all live in Postgres and survive
  restarts/redeploys.
- `VIGILENS_TRANSPORT` = `synthetic` in this package.
- `VIGILENS_LIVE_DISPATCH` - absent/off. Real provider calls stay disabled;
  enabling them is a separate owner-approved step after the durable spend
  records are audited, never set by this package.
- `VIGILENS_LOCAL_ACCESS_TOKEN` - set in the dashboard (`sync: false`), SAME
  value on both services. Server-side only; it never ships in the JS bundle
  (bundle-grep verified 2026-11-01).
- `VIGILENS_FRONTEND_ORIGINS` - the frontend URL (CORS).
- `VIGILENS_CAP` - install cap in USD string (default `5`).

Frontend:
- `DATABASE_URL` - wired from the database by the blueprint.
- `BETTER_AUTH_SECRET` - generated by the blueprint.
- `VIGILENS_BACKEND_URL` - the backend's assigned onrender URL; verify the
  actual hostname at deploy. Proxies same-origin `/api/vigilens/*`.
- `VIGILENS_LOCAL_ACCESS_TOKEN` - same value as the backend's.

## Boot integrity

Boot seeds and pins the carry/approvals documents by sha in Postgres and
migrates the schema in place (never drops existing rows; legacy ownerless rows
stay internal-only). Every request re-verifies retained artifacts, accounting
and document pins against the database, so mid-operation tamper fails closed
rather than serving stale state.

## Restart / redeploy / sleep behavior (PG mode)

- Persisted state survives: stored jobs, calls, accounting, approvals, and
  SUBMITTED zone/contact/rule reviews - they are rows in Postgres.
- Preview sessions are memory-only and do NOT survive a restart, redeploy, or
  free-tier sleep wake: the private-display session itself, its preview
  acknowledgment, and any unsubmitted zone/rule/contact edits held in that
  session are lost and must be redone. The stored analysis is NOT lost: the
  visitor re-uploads the EXACT same image bytes, the claim finds the stored
  completed job and returns it with ZERO redispatch and ZERO new charge, and
  the visitor re-acknowledges the preview to continue.
- Free services sleep after 15 min idle (~1 min cold start). The frontend
  polls `/health` and keeps analysis disabled until the backend answers.

## Hostnames and wiring to verify at deploy (do not presume defaults)

The blueprint ships placeholder hostnames. After the blueprint creates the two
services, Render assigns the real URLs. Verify and correct before demoing:
1. Backend service `VIGILENS_FRONTEND_ORIGINS` must equal the ACTUAL frontend
   URL (e.g. `https://vigilens-frontend-xxxx.onrender.com`), comma-separated if
   more than one. Wrong value = browser calls refused.
2. Frontend service `VIGILENS_BACKEND_URL` must equal the ACTUAL backend URL.
   Wrong value = every analysis call 503s ("backend not configured").
3. Backend `VIGILENS_DATABASE_URL` comes from the blueprint `fromDatabase`
   wiring (internal connection string; boot normalizes to sslmode=require).
   Do not replace it with the external string except for the pg_dump export
   described below. If it is missing, the backend silently falls back to
   EPHEMERAL sqlite state and the journal/ledger is lost on every restart -
   check the backend boot log for the "durable Postgres state" line.
4. `VIGILENS_LOCAL_ACCESS_TOKEN` is set by Aadi in the dashboard on BOTH
   services to the SAME value (generate a long random one locally; it never
   goes in chat, git, or this package).
5. `VIGILENS_TRANSPORT=synthetic` and `VIGILENS_LIVE_DISPATCH` unset/off for
   the trial: zero provider calls, zero spend.

## Free Postgres 30-day expiry (answer before relying on it)

Render deletes a free Postgres 30 days after creation. Creation date plus 30
days is the hard outer bound of this deployment's state - plan around the Nov 5
demo date, and do not assume state exists for any judging after expiry.

WARNING - an empty replacement database is NOT continuity. The budget ledger,
per-job accounting, and uncertain holds (the no-retry records) live in this
database. Recreating an empty database and repointing `DATABASE_URL` /
`VIGILENS_DATABASE_URL` loses them, and a lost hold means a previously charged
request could be retried and charged again. Never treat empty recreation as a
restore. The ONE acceptable empty replacement: the lost state was purely
synthetic demo data AND `VIGILENS_LIVE_DISPATCH` was never enabled, so no
charged request exists that a lost hold could re-charge.

If state must outlive the window:
1. BEFORE expiry, while the database is live, take a complete source-backed
   export: `pg_dump` the full `vigilens` database (both the better-auth
   tables and the pipeline store) over the database's EXTERNAL TLS connection
   URL from the Render dashboard, to private storage. Render's free Postgres
   has NO dashboard on-demand export and NO point-in-time recovery (paid
   tiers only) - this manual `pg_dump` is the only export route, and it must
   happen before the 30-day deletion.
2. Restore into the replacement database, then VERIFY state reconciliation
   before any traffic: job counts, accounting totals, carry/approvals document
   pins, and every uncertain hold must match the export.
3. Keep `VIGILENS_LIVE_DISPATCH` off (it is already off in this package) until
   that verification has passed; only then is the replacement equivalent.
If no export/restore with verified reconciliation has happened, the correct
posture is: demo-only state, expiry loses it, and nothing retries against the
lost records because the install is gone with them.

## Global bounds (disclosed)

- Install cap `VIGILENS_CAP` and the 64-job bound are GLOBAL across all visitor
  accounts by design (install-level safeguards), as are the reservation/mask/
  explanation totals used by cap accounting. Per-account namespaces isolate
  results, artifacts, calls and satellites; uncertain holds are journal-global
  (no-retry contract).
- Historical unreconciled call accounting exists from qualification; this
  package never projects per-call costs from it.

## Build/runtime resource caveats

- `pnpm build` (Nitro) OOMs on a 2GB local sandbox; Render's build environment
  is larger and is the intended build path.
- Free service runtime is 512MB - unmeasured for this app. Watch the first
  deploy's memory; if it OOMs at runtime the choices are a paid plan (Aadi's
  decision, not this package's) or a slimmed build.
