# Review, preview, report and zone endpoint contract (backend prepared; frontend wiring NOT done)

Status: these endpoints exist in the backend and are source-tested. They are NOT exposed through the launched proxy and NOT called by the current client (head 7a90eef calls only POST /audit and GET /health). The proxy audience is unchanged and no export is enabled. Examples are executable: tests/test_workflow_contract_examples.py (synthetic data, stub transport, zero provider calls) and frontend-contract-samples/workflow_contract.json (step, status, response keys, error detail).

Common: every route needs `X-Vigilens-Local-Access` (backend token, held by whoever calls the backend directly) and `X-Vigilens-Display-Session` (32-128 chars of A-Za-z0-9_-). Display sessions, contact claims and reports are bound to the value of that header by constant-time equality (a bearer secret: the backend checks only its format and equality, never an identity or account): a different session gets 404 (display session) or 409 (zones, contacts). Wrong or stale bindings return 409 with a fixed, non-revealing message. Nothing here calls the provider.

## Zone mapping: backend implementation still outstanding
The client's drawn zones are not used by POST /audit (zones_applied=false). The zone-review route takes the same normalised polygons (id, name, hazard, points) but needs the stored result hash, a reviewer label, and honest membership inputs. Missing: (a) a route or proxy mapping that validates the client's posted zones, binds them to the analysed result, and calls zone-review after a result exists; (b) a displayed state for membership, which stays "unknown" until a human contact claim exists (the backend never infers it); (c) qualification of that mapping with the actual drawn-zone path, including the result-hash binding. Not implemented and not ruled out.
