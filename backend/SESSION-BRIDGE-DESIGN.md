# Session bridge: design plus a default-off helper. NOT a working frontend flow.

CORRECTION: earlier versions contrasted "owner-bound" display sessions with "possession-bound" audit lookup. Code reading (fresh_review/display.py) shows display.owner_check only checks the FORMAT of the header (32-128 chars, A-Za-z0-9_-). Display sessions, contacts, zone reviews and the audit lookup are all bound to a caller-supplied bearer value by constant-time equality (display) or an in-memory (session, digest) set (audit). None is an account or identity. The difference between the two is only what they bind to: equality with the value stored at creation, versus a record that this value posted this exact image.

Threat model (local, single user): two bearer secrets protect the private routes: the backend token (X-Vigilens-Local-Access) and the display-session value. Anyone holding both can read that session's previews and reviews. A proxy that holds the token and mints the session value therefore concentrates trust in the proxy cookie (HttpOnly, SameSite=Strict, idle 30 min, absolute 4 h, logout) and in the loopback machine. Not multi-user, not multi-tenant, not deployable as such.

What exists: local_ui_proxy.display_session_for(secret, sid) derives a backend session value by HMAC so the cookie value is never the backend value; local_ui_proxy.bridge_allowed(method, path, allowlist) returns True only for an explicitly enabled (method, name) with a strict path shape. The allow-list is empty and only GET zone-review has a shape. bridge_allowed is not used by any route, while display_session_for is used by POST /audit. Tests prove bridge_allowed is default-off and strict, that create_proxy does not reference bridge_allowed, and that the backend receives the derived value instead of the cookie id. Default-off is a code default, not a hard lock: a code edit enables it. UPDATE (post clean-v3): POST /audit now forwards display_session_for(proxy_secret, cookie_sid) instead of the cookie id. proxy_secret is 32 random bytes made at proxy start, held in memory only, never persisted, printed or sent; it dies with the proxy, as do the cookie sessions. The derived value is 64 hex chars (passes the backend's 32-128 format check) and is stable within a cookie session, so the backend's in-memory (session, digest) binding and the proxy idempotency replay keep working within a session. Logout or expiry is PROXY revocation only: the cookie id is dropped and the proxy will not derive that value again, but backend bindings and display sessions are not revoked and stay in backend memory until it restarts or they expire. Anyone already holding the backend token plus the derived value can still use them. A proxy restart changes both the secret and the cookie ids, so the proxy can no longer produce earlier values, but copied values stay valid at the backend. The separation means a leaked backend value does not directly reveal the cookie. It is not stronger authentication and does not defend against every compromise: the HttpOnly cookie remains the only browser-side credential, and a local process that reads proxy memory gets everything.

Not built: any proxy route for zone-review, contacts or private display; any frontend call. The unchanged client never sends these requests. Enabling needs a privacy/security review, Muse review, and frontend wiring that is out of scope here. Exports stay off.

Terminology: the function display.owner_check keeps its name, but it only checks the FORMAT of a bearer value. It checks no owner, account or identity. Anywhere 'owner' appears in these docs or code comments, read 'bearer session value'.
Review scope so far (Muse, by code read): display.py, the proxy helpers and the forwarding line. The backend audit handler's in-memory (session, digest) binding and the full test suite were not independently verified by Muse.
